# Security Remediation Report

Scope: the 5 P0/P1 findings from `07_FRONTEND_IAM_SECURITY_AUDIT.md` selected for remediation in this pass. Live backend authorization testing (anonymous/learner/reviewer/admin role matrix) was **not possible** — see `AUTH_SMOKE_TEST_REPORT.md` for why (a pre-existing local JDK/Windows networking bug blocks starting the Spring Boot backend on this machine, unrelated to this work). Every fix below was verified by: source re-reading before editing, `tsc`, `eslint` on touched files, a full production build, and (for the backend change) an offline Maven compile. None were verified by an actual authenticated HTTP request against a running instance — flagged explicitly per item.

## What was actually verified vs. traced by hand

Being precise about the difference, per the task's explicit instruction not to claim verification that didn't happen:

- **Verified against real output**: `ROUTE-002` (build artifact inspection), and every fix's non-regression (clean `tsc`, clean `eslint` on touched files, clean full production build across all 72 routes, offline `mvn compile` for the Java change).
- **Traced by hand, not executed**: the SSRF validator's logic against each named test case (below), the sanitizer's expected behavior against each named payload class (relying on DOMPurify's own well-established correctness rather than re-testing it from scratch), and the backend permission check's expected pass/fail per role (based on reading `IamBootstrap.java`'s seed data directly, not by making authenticated requests as each role).
- **Not verified at all**: full end-to-end behavior of any of these fixes through a running app with a running backend.

### SSRF validator — hand-traced against the required test cases

| Case | Expected | Why |
|---|---|---|
| Allowed media source (real https presigned URL, public host) | Passes | `https:` scheme, non-private resolved IP |
| Invalid URL (malformed string) | Rejected | `new URL()` throws → caught → 400 |
| `localhost` | Rejected | Explicit hostname check |
| `127.0.0.1` | Rejected | `isIP()` + loopback range check on the literal |
| Private IP ranges (`10.x`, `172.16-31.x`, `192.168.x`) | Rejected | Explicit range checks, both as literals and as DNS-resolved addresses |
| Cloud metadata address (`169.254.169.254`) | Rejected | Covered by the `169.254.0.0/16` link-local range check |
| Unsupported scheme (`http:`, `file:`, `javascript:`, `ftp:`) | Rejected | `url.protocol !== 'https:'` check |
| Redirects | Rejected | `redirect: 'manual'` + explicit check for 3xx/`opaqueredirect` |
| Malformed URLs | Rejected | Same as "invalid URL" |
| Hostname that resolves to a private IP (DNS rebinding) | Rejected | `dns.resolve4`/`resolve6` + range check on resolved addresses, not just the literal hostname |

## SECURITY status: **partially fixed, unresolved-pending-live-verification**

All 5 items have a source-level fix that compiles/type-checks/builds cleanly and was reasoned through against the specific failure mode. None have been exercised against a live backend or real browser session, because none could be — see `AUTH_SMOKE_TEST_REPORT.md`. This is not the same as "fixed and verified," and should not be reported as such upstream without a follow-up manual/live pass.
