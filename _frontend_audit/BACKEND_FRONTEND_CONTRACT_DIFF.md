## Pagination contract

**Backend reality** (confirmed, unchanged): every paginated endpoint returns raw Spring Data `Page<T>` — `{ content, pageable, last, totalPages, totalElements, size, number, sort, first, numberOfElements, empty }`. No custom envelope exists anywhere in the backend.

**Frontend reality**: no shared `PageResponse<T>` type exists in `shared/types/`. Instead, individual files define their own minimal local interface, and the completeness varies:

- `domains/notifications/api/notification.service.ts`: `interface Page<T> { content: T[] }` — only unwraps `content`, discards `totalElements`/`totalPages`/etc. entirely. This works for the notification feed's current UI (which doesn't show a page count), but means this file *cannot* currently support "page 3 of 12"-style UI without being extended.
- `app/(authenticated)/console/payments/page.tsx` (per the original API audit): does use `totalPages`/`totalElements`/`number`/`size` for its pagination controls — a fuller local usage.
- 20 files total reference `totalElements`/`totalPages`/`content:` patterns (grepped in this pass), confirming pagination handling is real and functional across the app, just duplicated ad hoc rather than sharing one type.

**Assessment against the task's specific concerns**:
- *"Frontend assuming arrays instead of Page"* — not found as a live bug in this pass's sampling (`NotificationService.list()` unwraps to an array *deliberately*, matching what its UI needs, not by mistake).
- *"Client-side pagination over entire datasets"* — not independently re-verified this pass; the original performance audit (`PERF-002`) flagged this as a risk for catalog-style screens without confirming it empirically. Not re-checked here.
- *"Inconsistent page numbering / page size"* — not found; every sampled file uses the backend's own 0-indexed `page`/`size` query params directly, matching the backend's `Pageable` binding.
- *"Custom pagination formats"* — not found; nothing invents its own pagination envelope. The gap is duplication (many local partial `Page<T>` interfaces) rather than incompatibility.

**Recommended fix** (not implemented in this pass, per "adapt the data layer to the existing UI first, do not redesign the UI" — this is a data-layer typing improvement, not a UI change, but batching it into every consumer is exactly the kind of broad migration this task deferred): add one shared `shared/types/pagination.ts` exporting the full Spring `Page<T>` shape, and have new/migrated domain query hooks (per `DATA_LAYER_STANDARD.md`) use it instead of each defining their own partial local interface. Existing local interfaces don't need to be ripped out proactively — they're not wrong, just incomplete for their current use — but every future React Query migration should reach for the shared type rather than writing a fourth or fifth local `Page<T>`.
